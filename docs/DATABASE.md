# Базы данных платформы

С 26.09.2026 все данные платформы хранятся в PostgreSQL. Каждый раздел платформы работает со своей базой, у каждого сервиса своя
роль с доступом только к нужным базам. Файлов данных в репозитории и коммитов в Git платформа больше не создаёт.

## 1. Что было не так

До перехода данные жили в трёх местах, и ни одно не подходило для реального запуска.

| Слабое место | Как было | К чему приводило |
|---|---|---|
| Пользовательские данные не сохранялись централизованно | Заявки, предложения, отклики, регистрации представителей, решения модератора, профиль и цепочки на сайте sm01.xroyse.ru сохранялись в `localStorage` браузера автора. API держал свои копии в памяти процесса (`OFFERS`, `REQUESTS`, `REGISTRATIONS`, `NOTIFY`, `AUDIT`, лента уведомлений, привязки Telegram) | Модератор не видел регистраций и заявок, покупатель — предложений других пользователей. После перезапуска API всё терялось. В локальном режиме модератором считался любой посетитель (`canEdit = true`) |
| Правила доступа на стороне браузера | Кто что видит и может менять, решал JavaScript сайта | Любой мог изменить или удалить чужую запись, подделать решение модератора |
| 18 МБ JSON при каждом открытии сайта | `site/data.json` — все 4536 карточек целиком: 18 149 источников (6,7 МБ одинаковых записей ФНС), история изменений, отчётность за 3 года, налоги. nginx отдавал файл без сжатия | Долгая загрузка на слабом интернете, 18 МБ разбора JSON на телефоне; каждый сбор добавлял сотни карточек |
| Тысячи файлов в Git | `data/companies/<id>/{company,products,sources}.json` — 13 608 файлов, плюс дубликаты `data/products/*.json` и `data/sources/sources.json`, плюс `site/data.json` | Медленный Git; тест синхронизации копировал весь `data/` перед каждым тестом — 16 тестов шли 12 мин 16 с; каждый ежедневный сбор давал огромный коммит, обновление сервера требовало `git commit` данных и слияния `-X ours` |
| Схема PostgreSQL не использовалась | `backend/sql/schema.sql` описывал одну общую базу, API её не читал | Каталог, персональные данные и журналы сбора оказались бы в одной базе с одним паролем |
| Файлы управления сбором | `data/sync/run.lock`, `status.json`, `run-request.json` | Блокировка по времени изменения файла, общий том между контейнерами API и сбора |

## 2. Архитектура

Один сервер PostgreSQL 16, шесть баз. Разделение по разделам платформы: у каждой базы свой владелец данных, свой режим записи и свой
срок жизни данных, их можно резервировать, восстанавливать и переносить на другой сервер по отдельности.

```
                        ┌─────────────────────── PostgreSQL ───────────────────────┐
  sync (pk_sync) ──────►│ sm01_catalog    каталог предприятий         ◄── api: чтение │
  краулер (pk_crawler) ►│ sm01_ingest     сбор данных, журналы         ◄── api: запуск │
                        │                                                           │
  api (pk_api) ────────►│ sm01_accounts   пользователи, кабинет, ПДн                │
                        │ sm01_market     предложения, заявки, отклики              │
                        │ sm01_chains     производственные цепочки                  │
                        │ sm01_moderation регистрации, решения, правки, аудит       │
                        └───────────────────────────────────────────────────────────┘
```

| База | Раздел | Пишет | Читает | Объём (26.09.2026) |
|---|---|---|---|---|
| `sm01_catalog` | Каталог предприятий: реквизиты, продукция, источники, риски, отчётность, справочники | `sync`, загрузка из JSON | API (в памяти процесса), краулер | 29 МБ, 4536 предприятий |
| `sm01_ingest` | Сбор данных: запуски, изменения, ошибки, блокировка, ручной запуск, поиск и обход сайтов | `sync`, краулер; API — только запрос запуска и задачи обхода | API, админ-панель | 9 МБ |
| `sm01_accounts` | Пользователи, сессии, личный кабинет, настройки и лента уведомлений, привязки Telegram. **Единственная база с персональными данными** (152-ФЗ) | API | API | — |
| `sm01_market` | Биржа: предложения, заявки, подобранные поставщики, отклики | API | API | — |
| `sm01_chains` | Производственные цепочки: этапы, поставщики, связи, история замен | API | API | — |
| `sm01_moderation` | Регистрации представителей (реквизиты компании), решения модератора, подтверждённые представители, ручные статусы, решения по записям, правки продукции, отключённые источники, сообщения об ошибках, аудит | API | API | — |

### Роли и права

Роли создаёт `python -m pkdb.migrate --roles` (в Docker — сервис `migrate` при каждом запуске):

| Роль | catalog | ingest | accounts | market | chains | moderation |
|---|---|---|---|---|---|---|
| `pk_api` | чтение | чтение; запись `sync_request`, `crawl_job`, `site_discovery` (решение модератора по найденному сайту) | чтение и запись | чтение и запись | чтение и запись | чтение и запись |
| `pk_sync` | чтение и запись | чтение и запись | нет доступа | нет доступа | нет доступа | нет доступа |
| `pk_crawler` | чтение | запись `crawl_log`, `crawl_page`, `crawl_job`, `crawl_run`, `site_discovery`, `site_search` | нет доступа | нет доступа | нет доступа | нет доступа |

Ошибка или уязвимость в сборе данных не открывает персональные данные пользователей; API не может испортить каталог.

### Связи между базами

Внешний ключ между базами PostgreSQL невозможен, поэтому ссылки через границу баз — текстовые идентификаторы, их проверяет API:
предприятие (`company_id` в заявках, предложениях, цепочках, регистрациях) — при записи сверяется с каталогом; автор записи
(`author_id`, `owner_id`, `user_id`) — всегда тот, кто отправил запрос, поле `author` из запроса не принимается. Внутри базы связи —
обычные внешние ключи с каскадным удалением.

## 3. Схемы

Полные определения — `pkdb/schema/<раздел>.sql`. Принципы: у каждого факта ссылка на источник (`source_id`), неизвестное —
`NULL` (у ОКВЭД без названия в реестре название `NULL`, а не выдуманный текст), ограничения `CHECK` на статусы, уровни рисков,
цены и бюджеты. Поля, которых схема ещё не знает, не теряются: у таблиц есть столбец `extra jsonb`, значения возвращаются в карточку.

**sm01_catalog** — 26 таблиц. `company` (реквизиты, статус юрлица, статус проверки, состояние сверки с реестрами, полнотекстовый
индекс по-русски); дочерние таблицы карточки: `company_okved`, `company_technology`, `company_material`, `company_capacity`,
`company_certificate`, `company_site`, `company_capability` (возможности по ОКВЭД), `company_discrepancy` и `_value`,
`company_risk_signal`, `company_registry` (недоимка, численность, налоги, МСП, руководитель), `company_finance` (отчётность по годам),
`company_history`; `source` — источники карточки; `product`, `product_param`, `product_material`; `relation` — связи предприятий;
справочники `region`, `city`, `okved`, `okpd2`, `material`, `technology`; `catalog_revision` — ревизия каталога.

**sm01_ingest** — `sync_run`, `sync_change`, `sync_error` (журнал каждого прохода), `sync_state` (состояние для админ-панели),
`sync_lock` (блокировка с отметкой жизни раз в минуту; не обновлялась 10 минут — процесс упал), `sync_request` (кнопка «Запустить
сбор»), `crawl_log`, `crawl_page`, `crawl_job` (очередь повторного обхода из админ-панели), `crawl_run` (запуски краулера: после
сбора или по очереди, итоги и когда найденное перенесено в карточки), `site_discovery` (домены, проверенные краулером при поиске официального сайта,
и чем сайт подтверждён), `site_search` (когда у предприятия искали сайт).

**sm01_accounts** — `app_user` (роль), `user_session` (только SHA-256 токена), `user_account` (ФИО, должность, e-mail, телефон,
согласие на обработку ПДн), `user_profile`, `user_company`, `user_favorite`, `user_compare`, `saved_search`, `company_claim`,
`warehouse`, `notify_channel`, `notify_event`, `inbox_notice`, `telegram_link`.

**sm01_market** — `offer`, `purchase_request`, `request_supplier`, `request_response`.

**sm01_chains** — `chain`, `chain_node`, `chain_node_history`, `chain_edge`.

**sm01_moderation** — `registration` (реквизиты компании без контактов представителя), `registration_decision`, `company_rep`,
`status_override`, `item_decision`, `product_edit`, `source_flag`, `report`, `audit_log`.

## 4. Как данные доходят до сайта

1. **Сбор** (`python -m sync`) загружает каталог из `sm01_catalog`, сверяет с реестрами и одной транзакцией записывает изменённые
   карточки, увеличивая `catalog_revision`. Журнал прохода — в `sm01_ingest`.
2. **API** держит каталог в памяти (для подбора поставщиков по всем карточкам) и проверяет ревизию не чаще раза в 5 секунд
   (`PK_REVISION_TTL`); изменилась — перечитывает. Поверх накладываются решения модератора: ручные статусы и отключённые источники.
3. **Сайт** загружает `GET /api/v1/bundle` — облегчённые карточки: без истории, отчётности, подробностей источников и пустых полей,
   источники реестров и риски сжаты, позиции реестра Минпромторга — тройками «номер, наименование, код» (описание и
   характеристики — в полной карточке). Ответ сжат заранее, с `ETag`; пока ревизия не изменилась, повторный заход получает `304`.
   Полная карточка — `GET /api/v1/companies/{id}` при открытии предприятия, сравнении или раскрытии строки в админ-панели.
4. **Пользовательские данные** сайт сохраняет сразу на сервер (`PUT /api/v1/store/{коллекция}/{id}`, `PUT /api/v1/me/profile`,
   `PUT /api/v1/me/chains/{id}`) и раз в 20 секунд забирает изменения других пользователей. Права проверяет сервер:

| Коллекция | Видят | Пишут |
|---|---|---|
| `offers`, `requests`, `responses` | все (отклонённые модератором — автор и модераторы) | автор; модератор |
| `reports` | модератор — все, пользователь — свои | автор; отметку `override` — модератор |
| `registrations`, `moderation` | пользователь — свою, модератор — все | регистрацию — сам пользователь, решение — модератор |
| `reps`, `overrides`, `decisions`, `sourceflags` | все | модератор |
| `product_edits` | все | каждый — только свой документ |

Сессия браузера — случайный токен от `POST /api/v1/session`. Модератор входит служебным токеном из `PK_TOKENS` (админ-панель,
поле «Токен модератора») или получает роль: `python -m pkdb.admin set-role <id> moderator`. Решения модератора и отклики сервер
дублирует в Telegram и ВКонтакте по настройкам получателя.

## 5. Перенос данных (выполнен 26.09.2026)

`python tools/json_to_pg.py` переносит `data/` и сразу проверяет перенос: читает всё из базы обратно и сравнивает с файлами.

| Что | Перенесено | Проверка |
|---|---|---|
| Предприятия (`data/companies/*/company.json`) | 4536 | каждая карточка совпадает с файлом |
| Продукция | 80 позиций | совпадает; `data/products/*.json` — дубликаты, совпадают с продукцией карточек |
| Источники | 18 149 | совпадают; `data/sources/sources.json` — производная копия, совпадает |
| Сигналы риска, отчётность, история | 3185 сигналов, 12 782 года отчётности, 4539 записей истории | в составе карточек |
| Справочники | 289 ОКВЭД, 18 ОКПД2, 7 регионов, 5 городов, 7 связей, материалы, технологии | совпадают |
| Журналы сбора `data/sync/*.json` | 4 прохода с изменениями и ошибками; `latest.json` — копия последнего | совпадают |
| Журнал обхода `data/sources/crawl_log_*.json` | 51 запись | совпадает |

Итог проверки: **расхождений нет**. Единственное отличие — суммы в JSON несли шум двоичной арифметики (`1130848.8399999999`),
`numeric` в базе хранит точные копейки (`1130848.84`).

Пользовательских данных на сервере не было: они жили в браузерах. Сайт переносит их сам — при первом заходе пользователя данные
из `localStorage` уходят на `POST /api/v1/me/import-local`. Переносится только созданное самим пользователем (предложения, заявки,
отклики, сообщения об ошибках, регистрация, правки продукции, профиль, цепочки). Решения модератора из браузера не переносятся:
в браузере их мог «принять» кто угодно.

После переноса `data/` и `site/data.json` исключены из Git (`.gitignore`). Файлы на диске остаются как исходник переноса;
удалить их можно после проверки. В истории Git старые версии данных сохраняются — очистка истории (`git filter-repo`) переписывает
опубликованную историю и требует отдельного решения.

### Продукция: откуда позиции

| Источник позиции | `source_id` | Код ОКПД2 | Как появляется |
|---|---|---|---|
| Первичный сбор (исследование 24.09.2026) | источник карточки | класс по классификатору, `INFERRED` | начальный набор `pkdb/seed` |
| Страница официального сайта | `<id>-web-<хеш адреса>` | класс по словарю, `INFERRED`, или нет | краулер: поиск сайта и обход → ежедневный сбор (`sync/sitecrawl.py`) или `tools/crawl_products.py auto`; позиции без отдельной страницы — модератору |
| Реестр промышленной продукции Минпромторга (ПП № 719) | `<id>-minprom` | из реестра, `SOURCE` | ежедневный сбор, файл раз в неделю (`docs/SYNC.md`) |

| Правка представителя предприятия | исходный источник | `COMPANY` | кабинет представителя (`sm01_moderation.product_edit`) |

На 26.09.2026 в каталоге 12 760 позиций у 184 предприятий: 12 474 из реестра промышленной продукции Минпромторга
(175 предприятий), 169 с официальных сайтов 7 предприятий (обход 930 страниц на сайтах 13 предприятий), 80 первичного сбора, 37 из реестра МСП
(3 предприятия). 71 из 80 позиций первичного сбора подтверждены на сайтах при обходе.

До 26.09.2026 позиций было 80: столько собрал первичный сбор 24.09.2026, а сбор из реестров добавлял предприятия с реквизитами,
отчётностью и рисками, но без продукции. При переносе в PostgreSQL ничего не потеряно — 80 позиций было и в JSON (раздел 5).
Остальные ~4350 предприятий базы продукцию в официальных источниках не публикуют: их нет в реестре Минпромторга, реестр МСП
заполнен у 0,15 % субъектов, сайт известен у немногих. Для них позиции появятся от представителей предприятий (кабинет) или
после поиска официальных сайтов.

## 7. Эксплуатация

| Задача | Команда |
|---|---|
| Создать базы, применить схемы, роли | `python -m pkdb.migrate --roles` (Docker: сервис `migrate`) |
| Заполнить пустой каталог начальным набором | `python -m pkdb.seed` (28 предприятий первичного сбора из `pkdb/seed/`) |
| Перенести прежнюю базу из JSON | `python tools/json_to_pg.py --data-dir путь/к/data` |
| Проверить качество данных каталога | `python tools/validate_data.py` |
| Выгрузить каталог для просмотра без сервера | `python tools/export_bundle.py` → `site/data.json` |
| Назначить модератора | `python -m pkdb.admin set-role <id> moderator` |
| Резервная копия | `pg_dump -Fc sm01_<раздел>` для каждой базы (docs/INSTALL.md, раздел 12) |

Изменение схемы — новый файл `pkdb/schema/<раздел>/002_что_меняется.sql`: `pkdb.migrate` применит его один раз и запишет версию
в `schema_migrations` этой базы. После добавления таблиц повторите `--roles`, чтобы роли получили права на них.

Адреса баз: `PK_PG_URL` (сервер; имя базы — `PK_DB_PREFIX` + раздел, по умолчанию `sm01_`) или отдельный адрес для каждой базы
`PK_DB_URL_CATALOG`, `PK_DB_URL_ACCOUNTS` и т. д. — например, чтобы вынести базу с персональными данными на отдельный сервер.

Тесты поднимают отдельные базы `sm01test_*` (рабочие не трогают): сервер из `PK_TEST_PG_URL` или встроенный PostgreSQL
(пакет `pgserver`).
