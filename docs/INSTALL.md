# Установка платформы на Linux-сервер (Ubuntu + Docker)

Инструкция для администратора сервера. По ней платформа «Промышленная кооперация» разворачивается на сервере с Ubuntu: сайт по HTTPS на вашем домене, API, ежедневный сбор данных из реестров ФНС и Федресурса в 00:01 и кнопка ручного запуска сбора в админ-панели.

Время установки: около часа. Первый полный сбор базы компаний идёт ещё 4–5 часов, в фоне.

## 1. Что будет установлено

Все части запускаются через Docker Compose из файла `docker-compose.yml` в корне проекта.

| Сервис | Что делает | Где слушает |
|---|---|---|
| `web` | nginx: отдаёт сайт и передаёт запросы `/api/` серверу API | `127.0.0.1:8080` |
| `api` | сервер API (FastAPI): каталог, поиск, заявки, регистрация, модерация, уведомления, запуск сбора | `127.0.0.1:8000` |
| `sync` | планировщик сбора: каждый день в 00:01 и по кнопке в админ-панели сверяет базу с реестрами и добавляет новые компании | — |
| `db` | PostgreSQL 16: все данные платформы, у каждого раздела своя база | внутри Docker |
| `migrate` | при каждом старте создаёт недостающие базы, применяет схемы и выдаёт права ролям сервисов, затем завершается | — |
| `redis` | Redis: для очередей следующих версий | внутри Docker |
| `crawler` | обход сайтов предприятий (Scrapy), запускается вручную | — |

Снаружи сервер открыт только через HTTPS-прокси Caddy (раздел 8), он же получает и продлевает сертификат Let's Encrypt. Порты 8080 и 8000 доступны только на самом сервере.

```
посетитель ──HTTPS──► Caddy :443 ──► web (nginx) :8080 ──► сайт (site/dist)
                                               └── /api/ ──► api :8000 ──► PostgreSQL: каталог (чтение), пользователи, биржа,
                                                                           цепочки, модерация (чтение и запись)
                                   sync ──► реестры ФНС и Федресурса ──► PostgreSQL: каталог и журналы сбора
```

Все данные платформы хранятся только в PostgreSQL (том Docker `pgdata`), у каждого раздела своя база — подробно в [docs/DATABASE.md](DATABASE.md):

| База | Что в ней | Кто пишет |
|---|---|---|
| `sm01_catalog` | предприятия, продукция, источники, риски, отчётность, справочники | `sync`, краулер |
| `sm01_ingest` | запуски сбора, изменения, ошибки источников, ручной запуск, журнал обхода | `sync`, краулер; API ставит запрос запуска |
| `sm01_accounts` | пользователи, сессии, личный кабинет, уведомления — **персональные данные** | `api` |
| `sm01_market` | предложения, заявки, отклики | `api` |
| `sm01_chains` | производственные цепочки | `api` |
| `sm01_moderation` | регистрации представителей, решения модератора, правки продукции, аудит | `api` |

Сервисы подключаются к базам под своими ролями: `api` видит каталог только на чтение, `sync` не имеет доступа к базам пользователей. Файлов данных в папке проекта и коммитов в Git платформа не создаёт. В папке остаётся только кеш `Trash/opendata/` (том `opendata-cache`) — скачанные наборы открытых данных: ФНС — до 600 МБ, раз в месяц; реестр промышленной продукции Минпромторга — около 420 МБ, раз в неделю; реестр МСП (если включён `PK_SYNC_RMSP=1`) — ещё около 2 ГБ.

## 2. Требования

**Сервер**

| | Минимум | Рекомендуется |
|---|---|---|
| Система | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS |
| Процессор | 2 ядра | 2–4 ядра |
| Память | 2 ГБ | 4 ГБ |
| Диск | 20 ГБ SSD | 40 ГБ SSD |

**Размещение в России.** Сайты ФНС (egrul.nalog.ru, pb.nalog.ru, bo.nalog.gov.ru) могут не отвечать на запросы с зарубежных адресов, и тогда сбор данных не работает. Кроме того, платформа хранит персональные данные представителей компаний, а по 152-ФЗ их нужно хранить в России. Берите сервер у российского провайдера.

**Сеть**

- входящие порты: 22 (SSH), 80 и 443 (сайт; 80 нужен для получения сертификата);
- исходящий доступ в интернет: реестры ФНС и Федресурса, Docker Hub, PyPI (при каждом запуске сервис `sync` ставит библиотеку httpx), GitHub;
- домен или поддомен, например `koop.example.ru`, с A-записью на IP сервера. Запись должна начать работать до раздела 8.

**Что понадобится от вас**

- доступ к серверу по SSH с правами sudo;
- доступ к управлению DNS домена;
- если нужны уведомления — токен бота Telegram и ключ сообщества ВКонтакте (раздел 11).

## 3. Подготовка сервера

Подключитесь к серверу и обновите систему:

```bash
ssh ваш-пользователь@IP-сервера
sudo apt update && sudo apt upgrade -y
sudo apt install -y git curl ca-certificates openssl
```

Часовой пояс сервера нужен для журналов; время сбора задаётся отдельно, переменной `TZ` в `.env`:

```bash
sudo timedatectl set-timezone Europe/Volgograd
```

Брандмауэр — открыть только SSH и веб:

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status
```

> Docker публикует порты в обход ufw. В `docker-compose.yml` порты сайта и API привязаны к `127.0.0.1`, поэтому снаружи они не видны. Не меняйте эту привязку на `0.0.0.0`.

## 4. Установка Docker

Ставим Docker Engine и плагин Compose из официального репозитория Docker:

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
```

Проверка:

```bash
sudo docker run --rm hello-world
docker compose version
```

Если Docker Hub недоступен с сервера, настройте зеркало реестра у вашего провайдера (`/etc/docker/daemon.json`, параметр `registry-mirrors`) и перезапустите Docker: `sudo systemctl restart docker`.

## 5. Получение платформы

Проект ставится в `/opt/promkoop`. Все команды дальше выполняются из этой папки через sudo: сервис сбора пишет файлы базы от имени root.

```bash
sudo git clone https://github.com/DigitalRevision/Cooperation-Web-Agent.git /opt/promkoop
cd /opt/promkoop
sudo git log -1 --oneline
```

Чтобы поставить конкретный выпуск, а не последнюю версию, переключитесь на его тег. Кнопка сбора в админ-панели, ежедневный запуск в 00:01 и настройки из этой инструкции есть начиная с выпуска v1.8:

```bash
sudo git checkout v1.8
```

Сайт уже собран и лежит в `site/dist/`, отдельная сборка не нужна.

## 6. Настройки: файл .env

Создайте файл настроек из образца:

```bash
cd /opt/promkoop
sudo cp .env.example .env
sudo chmod 600 .env
```

Сгенерируйте токен администратора API и пароли баз (владельца и ролей сервисов):

```bash
openssl rand -hex 32   # токен администратора
openssl rand -hex 24   # пароль владельца баз (PK_DB_PASSWORD); повторите для PK_API_DB_PASSWORD и PK_SYNC_DB_PASSWORD
```

Откройте файл (`sudo nano .env`) и заполните:

| Переменная | Что указать |
|---|---|
| `PK_TOKENS` | JSON с токенами и ролями, в одинарных кавычках: `'{"токен-админа":"admin"}'`. Можно добавить модератора: `'{"токен-1":"admin","токен-2":"moderator"}'`. Роли: `user`, `company_admin`, `moderator`, `admin` |
| `PK_DB_PASSWORD` | пароль владельца баз. Задайте до первого запуска: при первом старте он записывается в базу, и потом его меняют уже в самой базе |
| `PK_API_DB_PASSWORD`, `PK_SYNC_DB_PASSWORD` | пароли ролей `pk_api` и `pk_sync`, под которыми работают API и сбор. Сервис `migrate` выставляет их при каждом запуске, поменять можно в любой момент |
| `PK_CRAWLER_DB_PASSWORD` | пароль роли `pk_crawler`, под которой работает краулер (ищет и обходит сайты предприятий после каждого сбора). Без него краулер не подключится к базе |
| `PK_TG_BOT_TOKEN`, `PK_VK_GROUP_TOKEN`, `PK_TG_WEBHOOK_SECRET` | для уведомлений, раздел 11. Можно оставить пустыми |
| `PK_SYNC_AT` | время ежедневного сбора, по умолчанию `00:01` |
| `TZ` | часовой пояс, в котором считается это время, по умолчанию `Europe/Volgograd` |
| `PK_SYNC_MIN_REVENUE_K` | порог выручки новой компании, тыс. ₽. Не меньше 1: компании без выручки не добавляются |
| `PK_SYNC_MAX_NEW` | сколько новых компаний добавлять за один сбор, по умолчанию 5000 |
| `PK_SYNC_MPT_DAYS` | как часто скачивать заново реестр промышленной продукции Минпромторга (около 420 МБ), дней; по умолчанию 7 |
| `PK_SYNC_RMSP` | `1` — загружать продукцию и названия кодов ОКПД2 из реестра МСП ФНС (архив около 2 ГБ раз в месяц); по умолчанию выключено |
| `PK_CHECKO_KEY` | необязательно: ключ платного Checko API (арбитражные дела, ФССП, реестр недобросовестных поставщиков) |

Пример заполненного файла:

```ini
PK_TOKENS='{"3f9c2e...b71a":"admin"}'
PK_DB_PASSWORD=8d1f0c9a4b2e7c55a1f3e0d9c6b8a742aa01
PK_API_DB_PASSWORD=5b0e...c21f
PK_SYNC_DB_PASSWORD=91aa...7d0e
PK_CRAWLER_DB_PASSWORD=4c7e...a90b
PK_TG_BOT_TOKEN=
PK_VK_GROUP_TOKEN=
PK_TG_WEBHOOK_SECRET=
PK_SYNC_AT=00:01
TZ=Europe/Volgograd
PK_SYNC_MIN_REVENUE_K=1
PK_SYNC_MAX_NEW=5000
PK_CHECKO_KEY=
```

Сохраните токен администратора в менеджере паролей: он понадобится для кнопки сбора в админ-панели.

> Без `PK_TOKENS` в `.env` на сервере не работает ни один токен, в том числе тестовые `dev-user` и `dev-admin` из кода. Это сделано намеренно, чтобы сервер нельзя было открыть общеизвестным токеном.

## 7. Первый запуск

Проверьте, что Compose читает настройки без ошибок:

```bash
cd /opt/promkoop
sudo docker compose config --quiet && echo "настройки в порядке"
```

Соберите и запустите сервисы:

```bash
sudo docker compose up -d --build
```

Первый запуск скачивает образы и собирает API, это 3–5 минут. Проверьте, что все сервисы работают:

```bash
sudo docker compose ps
```

У `web`, `api`, `sync`, `db` и `redis` должно быть состояние `running` (`Up`), у `migrate` — `exited (0)`: он создал базы и завершился. `crawler` в списке не появится: его запускают вручную. Если `migrate` завершился с ошибкой: `sudo docker compose logs migrate`.

Если вы переходите с прежней версии, где база хранилась в папке `data/`, перенесите её сейчас — раздел 7.1. При новой установке `migrate` загружает в пустой каталог начальный набор — 28 предприятий первичного сбора (`pkdb/seed`), остальное добавит первый сбор (раздел 10).

Проверьте сайт и API на самом сервере:

```bash
curl -s -o /dev/null -w "сайт: %{http_code}\n" http://127.0.0.1:8080/
curl -s http://127.0.0.1:8080/api/v1/meta; echo
```

Ожидаемо: `сайт: 200` и JSON вида `{"data_revision":1,"companies":4536,"products":80,"sources":...}` (после переноса из `data/`; при новой установке `companies` — 28 до первого сбора).

Проверьте планировщик сбора:

```bash
sudo docker compose logs --tail 20 sync
```

В журнале должна быть строка `планировщик: ежедневно в 00:01, следующий запуск …`.

Автозапуск после перезагрузки сервера уже настроен: у всех постоянных сервисов в `docker-compose.yml` стоит `restart: unless-stopped`, а Docker стартует вместе с системой. Проверить можно так:

```bash
sudo reboot
# после перезагрузки
cd /opt/promkoop && sudo docker compose ps
```

### 7.1. Перенос базы из прежней версии (папка data/)

В прежних версиях база предприятий хранилась файлами в `data/` и в Git. Перенос выполняется один раз; после него файлы не нужны,
но удалять их стоит только после проверки.

```bash
cd /opt/promkoop
sudo docker compose stop sync            # чтобы сбор не начался во время переноса
sudo docker compose run --rm -v "$PWD/data:/data:ro" -e PK_PG_URL="postgresql://promkoop:$(grep ^PK_DB_PASSWORD .env | cut -d= -f2)@db/postgres" \
  migrate python tools/json_to_pg.py --data-dir /data
sudo docker compose start sync
```

Скрипт переносит карточки, продукцию, источники, справочники, журналы сбора и обхода, затем читает всё из базы обратно и сравнивает
с файлами. В конце должно быть `перенос проверен, расхождений нет`. Повторный запуск откажется работать, если каталог уже заполнен;
перенести заново с очисткой — ключ `--replace`.

Заявки, предложения, регистрации и цепочки в прежней версии хранились в браузерах пользователей. Их переносит сам сайт: при первом
заходе пользователя с его браузера данные отправляются на сервер (`POST /api/v1/me/import-local`). Переносится только то, что
пользователь создал сам; решения модератора, принятые в браузере, не переносятся — их нужно принять заново.

## 8. Домен и HTTPS

Снаружи сайт открывается через Caddy: он принимает HTTPS на портах 80 и 443, сам получает и продлевает сертификат Let's Encrypt и передаёт запросы сервису `web`.

Убедитесь, что домен уже указывает на сервер:

```bash
dig +short koop.example.ru     # должен вернуть IP сервера
```

Установите Caddy из официального репозитория:

```bash
sudo apt install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | sudo gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' | sudo tee /etc/apt/sources.list.d/caddy-stable.list
sudo apt update
sudo apt install -y caddy
```

Настройте сайт. Замените `koop.example.ru` на ваш домен:

```bash
sudo tee /etc/caddy/Caddyfile > /dev/null <<'EOF'
koop.example.ru {
    encode gzip zstd
    reverse_proxy 127.0.0.1:8080
    header {
        Strict-Transport-Security "max-age=31536000"
    }
}
EOF
sudo systemctl reload caddy
```

Через минуту проверьте:

```bash
curl -sI https://koop.example.ru/ | head -1          # HTTP/2 200
curl -s https://koop.example.ru/api/v1/meta; echo    # JSON с числом компаний
```

Если сертификат не выдаётся, смотрите журнал Caddy: `sudo journalctl -u caddy --since "10 min ago"`. Чаще всего причина в том, что порт 80 закрыт или A-запись домена ещё не обновилась.

Если на сервере уже работает nginx или Apache и занимает порты 80 и 443, вместо Caddy добавьте в него сайт с проксированием на `http://127.0.0.1:8080` и заголовками `Host` и `X-Forwarded-For`, а сертификат получите через certbot.

## 9. Проверка работы

Откройте `https://koop.example.ru` в браузере и пройдите по списку:

1. **Главная.** Счётчики над поиском показывают число предприятий и регионов; кнопки быстрого ввода (например, «Сварка и контроль швов») находят предприятия.
2. **Каталог.** «Предприятия» и «Продукция» открываются, фильтры работают, карточка предприятия показывает реквизиты, риски и финансы.
3. **Админ-панель.** В подвале сайта — «Администрирование», вкладка «Сбор данных»:
   - в поле «Токен администратора API» введите токен из `PK_TOKENS`: он сохранится только в этом браузере;
   - статус должен стать «Планировщик работает», а в строке «Следующий запуск» — ближайшие 00:01;
   - если вместо этого «Сервер отказал в доступе», токен введён неверно или не совпадает с `.env`.
4. **API.** `https://koop.example.ru/api/v1/admin/sync` без токена должен отвечать `401`: это нормально.

## 10. Первый сбор данных

Сразу после установки в базе 28 предприятий начального набора. Полный список компаний машиностроения шести регионов (Волгоградская, Астраханская, Ростовская, Саратовская, Воронежская области, Калмыкия) — около 4,5 тысячи действующих компаний с выручкой. Их добавит сбор, двумя способами:

- **Подождать.** Планировщик сам запустит сбор в 00:01 (`PK_SYNC_AT`).
- **Запустить сейчас.** В админ-панели, вкладка «Сбор данных», кнопка «Запустить сбор сейчас». Сбор начнётся в течение 15 секунд; прогресс виден там же, например «1 500 из 4 558 компаний».

Первый полный сбор длится 4–5 часов. Дальше ежедневный сбор только сверяет базу и добавляет новые компании, это быстрее. Пока идёт сбор, второй не запустится: кнопка неактивна, а API отвечает `409`.

Ход сбора в журнале:

```bash
cd /opt/promkoop
sudo docker compose logs -f sync          # Ctrl+C — выйти из просмотра
```

Результат каждого сбора — сводка, изменения по компаниям и ошибки источников — записывается в базу `sm01_ingest` (таблицы `sync_run`, `sync_change`, `sync_error`). Каталог сбор пишет в `sm01_catalog` и увеличивает его ревизию: API перечитывает каталог сам в течение 5 секунд, сайт показывает новые данные после обновления страницы.

Подробности о сборе, источниках и правилах рисков — в [docs/SYNC.md](SYNC.md).

Поиск официальных сайтов и продукции предприятий краулером. Краулер работает так:

1. берёт предприятия из каталога (кроме ликвидированных);
2. ищет сайт, если его нет в карточке: домены по названию предприятия (несколько вариантов латиницей, аббревиатура, код
   региона, зоны .ru, .рф, .com, .su, .net, .org) и по корпоративной почте. На каждом живом домене читает главную,
   «Контакты», «Реквизиты», «О компании». Сайт подтверждён, если там ИНН или ОГРН предприятия либо его название вместе
   с улицей, домом и городом из адреса ЕГРЮЛ. Если совпало только название с городом, сайт ждёт решения модератора;
3. обходит сайт (известный или только что найденный): robots.txt, пауза 3 секунды между запросами к одному сайту,
   до 120 страниц на предприятие;
4. найденные сайты и страницы записывает в `sm01_ingest` (`site_discovery`, `site_search`, `crawl_page`, `crawl_log`). Карточки
   краулер не меняет: у него доступ к каталогу только на чтение.

Краулер — постоянный сервис `crawler` (`crawler/daemon.py`), запускается вместе с платформой (`docker compose up -d`)
и работает сам:

- **после каждого сбора из реестров** (ежедневно в `PK_SYNC_AT`, по умолчанию 00:01, и по кнопке «Запустить сбор»):
  поиск сайтов и обход всех известных сайтов. Первый запуск проверяет все предприятия без сайта (4,5 тыс. — около двух
  часов); повторно сайт предприятия ищется не раньше чем через `PK_DISCOVER_RECHECK_DAYS` дней (30), и обычный ночной
  запуск — это обход известных сайтов, около часа;
- **по заданиям из админ-панели:** кнопка «Повторить обход» во вкладках «Обход сайтов» и «Ошибки обхода» ставит адрес
  в очередь, краулер берёт её в течение минуты.

Каждый запуск записывается в `crawl_run` (вкладка «Обход сайтов» показывает последний). Как только запуск закончен,
планировщик сбора переносит найденное в карточки: подтверждённый сайт — в поле «Сайт» и источник «Официальный сайт» с тем,
чем он подтверждён; позиции со страниц каталога сайта — в продукцию (название дословно со страницы, источник — эта страница,
код ОКПД2 — класс по словарю со статусом «присвоено, требует подтверждения»), если у позиции есть признак товара:
характеристики на её странице, марка или модель в названии либо ещё одна позиция той же линейки. Остальное (пункты меню,
названия цехов, лозунги) ждёт модератора. Известные позиции, найденные на сайте, получают новую дату проверки. Нужен пароль
`PK_CRAWLER_DB_PASSWORD` в `.env`. Ход работы:

```bash
sudo docker compose logs -f crawler                                                    # что делает краулер
sudo docker compose run --rm crawler scrapy crawl company_sites                        # разовый обход вне расписания
sudo docker compose run --rm sync python tools/crawl_products.py auto                  # перенести в карточки вручную
```

Настройки краулера в `.env`: `PK_CRAWL_AFTER_SYNC=0` — не запускать после сбора, только задания из админ-панели;
`PK_DISCOVER=0` — только обход известных сайтов, без поиска; `PK_DISCOVER_LIMIT` — искать сайт не больше чем для
N предприятий за запуск (по умолчанию 20 000, крупные по выручке первыми, остальные — в следующие ночи; 0 — всех); `PK_DISCOVER_RECHECK_DAYS` — через сколько дней искать сайт снова.

Домены по названию находят сайт примерно у каждого седьмого предприятия. Остальным помогает поисковик: задайте
`PK_YANDEX_SEARCH_KEY` и `PK_YANDEX_FOLDER_ID` (Яндекс Search API в Яндекс Облаке, платно по тарифу Облака: создайте сервисный
аккаунт с ролью `search-api.webSearch.user`, выпустите для него API-ключ, идентификатор каталога — на странице каталога
в консоли). Тогда для предприятий, у которых домены по названию не подтвердились, краулер спросит «название город
официальный сайт» и проверит первые пять сайтов выдачи теми же правилами (справочники организаций и площадки пропускаются).
Один запрос на предприятие, не чаще 4 в секунду.

Сайты, у которых совпали только название и город, модератор подтверждает в админ-панели, вкладка «Найденные сайты»:
подтверждённый сайт ежедневный сбор запишет в карточку, а краулер обойдёт при следующем запуске. Позиции без отдельной
страницы в каталоге сайта и тот же список сайтов можно выгрузить в файл:

```bash
sudo mkdir -p /opt/promkoop/review
sudo docker compose run --rm -v /opt/promkoop/review:/review sync python tools/crawl_products.py auto --dry-run --review-out /review/crawl.json
# или прежний порядок с проверкой каждой позиции: review → решения в файле → apply
sudo docker compose run --rm -v /opt/promkoop/review:/review sync python tools/crawl_products.py review --out /review/crawl.json
# в crawl.json у кандидата decision: accept — записать, reject — нет, review — решить; можно поправить name, kind, category,
# params; decision "existing:<id позиции>" — это известная позиция
sudo docker compose run --rm -v /opt/promkoop/review:/review sync python tools/crawl_products.py apply /review/crawl.json
```

## 11. Уведомления в Telegram и ВКонтакте

Пользователи получают уведомления на сайте всегда, а копии в мессенджеры отправляет сервер API. Без этих настроек копии просто не отправляются, ошибок это не вызывает.

**Telegram**

1. Создайте бота у [@BotFather](https://t.me/BotFather) (`/newbot`) и скопируйте токен.
2. Придумайте секрет вебхука из латинских букв и цифр: `openssl rand -hex 16`.
3. Впишите оба значения в `.env` (`PK_TG_BOT_TOKEN`, `PK_TG_WEBHOOK_SECRET`) и перезапустите API:
   ```bash
   cd /opt/promkoop && sudo docker compose up -d api
   ```
4. Подключите вебхук: Telegram будет сообщать платформе, кто нажал `/start` у бота. Подставьте свои токен, домен и секрет:
   ```bash
   curl -s "https://api.telegram.org/bot<ТОКЕН_БОТА>/setWebhook" \
     -d "url=https://koop.example.ru/api/v1/notify/telegram/webhook" \
     -d "secret_token=<СЕКРЕТ_ВЕБХУКА>"
   ```
   Ответ должен содержать `"ok":true`.
5. Проверка: пользователь указывает свой @username в кабинете («Настройки → Уведомления в мессенджерах») и отправляет боту `/start`, после чего бот может ему писать. Без `/start` Telegram не разрешает ботам писать первыми.

**ВКонтакте**

1. В сообществе ВКонтакте: «Управление → Работа с API → Ключи доступа», создайте ключ с правом «Сообщения сообщества».
2. Включите сообщения сообщества: «Управление → Сообщения».
3. Впишите ключ в `PK_VK_GROUP_TOKEN` в `.env` и перезапустите API: `sudo docker compose up -d api`.
4. Пользователь указывает ссылку на свою страницу в кабинете и разрешает сообщения от сообщества.

## 12. Резервные копии

Копировать нужно:

- базы PostgreSQL — каждую отдельно (`pg_dump`), так их можно восстановить по одной: например, вернуть каталог, не трогая заявки пользователей;
- `.env` — настройки, токены и пароли.

Скрипт ежедневной копии с хранением за 14 дней:

```bash
sudo mkdir -p /var/backups/promkoop
sudo tee /usr/local/bin/promkoop-backup > /dev/null <<'EOF'
#!/bin/sh
set -e
cd /opt/promkoop
D=/var/backups/promkoop
T=$(date +%Y-%m-%d)
for db in catalog ingest accounts market chains moderation; do
  docker compose exec -T db pg_dump -U promkoop -Fc "sm01_$db" > "$D/sm01_$db-$T.dump"
done
cp .env "$D/env-$T"
find "$D" -type f -mtime +14 -delete
EOF
sudo chmod +x /usr/local/bin/promkoop-backup
echo "30 5 * * * root /usr/local/bin/promkoop-backup" | sudo tee /etc/cron.d/promkoop-backup
sudo /usr/local/bin/promkoop-backup && ls -lh /var/backups/promkoop
```

Копия делается в 05:30, после ночного сбора. База `sm01_accounts` содержит персональные данные: храните её копии так же бережно,
как сам сервер, и вне сервера — хотя бы раз в неделю переносите копии в другое хранилище в России.

Восстановление одной базы (пример — каталог):

```bash
cd /opt/promkoop
sudo docker compose stop sync api
sudo docker compose exec -T db pg_restore -U promkoop -d sm01_catalog --clean --if-exists < /var/backups/promkoop/sm01_catalog-ГГГГ-ММ-ДД.dump
sudo docker compose start api sync
```

## 13. Обновление платформы

Данные хранятся в PostgreSQL, в папке проекта только код, поэтому обновление — это `git pull` и пересборка. Схемы баз обновляет
сервис `migrate` при запуске: каждое изменение схемы применяется один раз.

```bash
cd /opt/promkoop
sudo git pull --ff-only
sudo docker compose up -d --build
sudo docker compose ps
```

Обновление на конкретный выпуск:

```bash
sudo git fetch --tags
sudo git checkout v1.8       # номер выпуска
sudo docker compose up -d --build
```

Если в новой версии изменились файлы сайта в `site/src/`, а `site/dist/` не пересобран, соберите его сами:

```bash
sudo docker run --rm -v /opt/promkoop:/w -w /w python:3.12-slim python tools/build_site.py
```

## 14. Повседневное управление

Все команды выполняются из `/opt/promkoop`.

| Задача | Команда |
|---|---|
| Состояние сервисов | `sudo docker compose ps` |
| Журнал сбора | `sudo docker compose logs -f sync` |
| Журнал API | `sudo docker compose logs -f api` |
| Перезапуск всего | `sudo docker compose restart` |
| Перезапуск после правки `.env` | `sudo docker compose up -d` |
| Остановка | `sudo docker compose down` (данные сохраняются) |
| Запустить сбор из консоли | `sudo docker compose exec sync python -m sync` |
| Проверка данных каталога | `sudo docker compose exec sync python tools/validate_data.py` |
| Консоль базы раздела | `sudo docker compose exec db psql -U promkoop sm01_catalog` |
| Назначить модератора | `sudo docker compose exec api python -m pkdb.admin set-role <id пользователя> moderator` |
| Занятое место | `sudo docker compose exec db psql -U promkoop -c "SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database WHERE datname LIKE 'sm01_%'"`; `sudo docker system df` |

Изменение времени сбора: поменяйте `PK_SYNC_AT` в `.env`, затем `sudo docker compose up -d sync`.

## 15. Решение проблем

| Что видно | Причина | Что сделать |
|---|---|---|
| Сайт не открывается по домену | не выдан сертификат или не работает прокси | `sudo journalctl -u caddy -n 50`; проверьте A-запись и что порты 80 и 443 открыты (`sudo ufw status`) |
| `502 Bad Gateway` | не запущен `web` или `api` | `sudo docker compose ps`, затем `sudo docker compose logs --tail 50 api web` |
| В админ-панели «Сервер отказал в доступе» | токен не совпадает с `PK_TOKENS` | проверьте токен в `.env`; после правки — `sudo docker compose up -d api` |
| «Планировщик не запущен» | остановлен сервис `sync` | `sudo docker compose up -d sync`, затем `sudo docker compose logs --tail 30 sync` |
| Кнопка сбора неактивна | сбор уже идёт | дождитесь окончания: прогресс на той же вкладке |
| В журнале сбора «требуется капча» | ФНС временно ограничила запросы к «Прозрачному бизнесу» | ничего: этот источник отложится до следующего сбора, остальные работают |
| Сбор находит 0 компаний, ошибки подключения к `nalog.ru` | сайты ФНС недоступны с адреса сервера (зарубежный IP) | нужен сервер в России (раздел 2) |
| `migrate` завершился с ошибкой, `api` и `sync` не стартуют | не заданы пароли ролей или база ещё не поднялась | `sudo docker compose logs migrate`; проверьте `PK_DB_PASSWORD`, `PK_API_DB_PASSWORD`, `PK_SYNC_DB_PASSWORD` в `.env`, затем `sudo docker compose up -d` |
| После обновления сайт показывает старое | браузер закэшировал страницу | обновите страницу с Ctrl+F5 |
| Заявки пользователя не видны модератору | сайт открыт как файл или без API (`/api/` не проксируется) | проверьте `curl -s http://127.0.0.1:8080/api/v1/meta`; сайт должен открываться с сервера платформы |

## 16. Ограничения текущей версии

- **Вход в кабинет привязан к браузеру.** Пользователь получает сессию при первом заходе; заявки, регистрация и цепочки хранятся на сервере, но с другого устройства в тот же кабинет пока не войти: нужен вход по e-mail (подтверждение по ссылке) — следующий этап. Модераторы входят токеном из `PK_TOKENS` или получают роль командой `python -m pkdb.admin set-role`.
- **Продукция новых компаний не собирается автоматически.** В реестрах ФНС и Федресурса нет списков продукции, поэтому новые компании попадают в базу без неё. Продукция есть у предприятий, собранных вручную, и появляется, когда её добавляют представители компаний.
- **Redis запускается, но пока не используется**: очереди обхода сайтов хранятся в `sm01_ingest`.
